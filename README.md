# Node Express HTTP API

Node.js / Express port of [`ruby-sinatra`](../ruby-sinatra), sharing the same
API contract: users (CRUD), products (queries) and payments (lifecycle), with
JSON bodies, validation and the same status codes. The project follows the same
layout as the original: `config/` boots the environment, `db/seeds/` holds the
fixtures, `src/` the application, `lib/` shared code, `test/` the suite and
`contract/` the machine-readable API contract.

## Stack

| Concern | Choice |
| --- | --- |
| Runtime | Node.js >= 20 |
| Web | [Express](https://expressjs.com/) 5 |
| ORM | [Prisma](https://www.prisma.io/) 6 |
| Database | SQLite (file per environment, under `storage/`) |
| Password hashing | `bcryptjs` (matches the original's bcrypt digest) |
| Logger | [Pino](https://getpino.io/) (`config/initializers/logger.js`, request logs via `src/middleware/request-logger.js`) |
| Seed data | YAML files under `db/seeds/data/` (parsed with `js-yaml`) |
| Tests | [Jest](https://jestjs.io/) + [Supertest](https://github.com/ladjs/supertest) under `test/` |

The schema mirrors `ruby-sinatra` exactly: three independent resources —
`users`, `products`, `payments` — with the same table and column names
(snake_case, via `@map`), the same unique index on `users.email`, and money
(`products.price`, `payments.amount`) stored as a decimal and exposed to
clients as text. See [`contract/database.sql`](contract/database.sql) and
[`contract/openapi.yml`](contract/openapi.yml).

## Layout

| Path | Responsibility |
| --- | --- |
| `config/boot.js` | Loads `.env`, resolves `APP_ENV`/`DATABASE_URL`/`PORT`/`HOST` |
| `config/environment.js` | Refuses an unknown `APP_ENV`, loads the environment settings and initializers |
| `config/environments/` | Per-environment settings (`development`, `test`, `production`) |
| `config/initializers/` | `database` (shared Prisma Client + database check) and `logger` |
| `config/initializers.js` | Loads the initializers in order |
| `src/app.js` | Express app factory (`createApp`, counterpart of `app.rb`) |
| `src/server.js` | Verifies the database, then starts the HTTP server |
| `src/middleware/request-logger.js` | Per-request log lines (`method`, `path`, `status`, `duration_ms`) |
| `src/routes/` | One router per resource: `users`, `products`, `payments` |
| `src/models/` | Validation rules, JSON shapes and Prisma data mapping |
| `src/helpers/` | `json` (body parsing), `records` (lookup/attributes), `params` (query filters) |
| `lib/errors/errors.js` | HTTP errors, 404/405 route table and the JSON error handler |
| `db/seeds/` | Idempotent seed: `data/*.yml` fixtures + `loaders/*` per resource, orchestrated by `index.js` |
| `test/` | Jest suite mirroring `ruby-sinatra/spec/`: `test/models/` (unit), `test/routes/` (integration via Supertest), `test/errors.test.js`, `test/logger.test.js`, wired by `test/test_helper.js` |
| `contract/` | `openapi.yml` (HTTP contract) and `database.sql` (schema contract) |
| `prisma/schema.prisma` | Data model: `User`, `Product`, `Payment` |
| `prisma/migrations/` | SQLite DDL generated by Prisma Migrate |
| `storage/` | SQLite files, one per environment (git-ignored) |

> Prisma resolves a relative SQLite path from the `prisma/` folder (where
> `schema.prisma` lives), so `DATABASE_URL` uses `file:../storage/<env>.sqlite3`
> to keep the databases at the project-root `storage/` directory.

## Getting started

```sh
npm install
cp .env.example .env          # development is the default
npm run db:setup              # migrate (dev) + seed
```

Tests and lint:

```sh
npm test                      # migrate the test db + run the suite (serial)
npm run lint                  # ESLint
```

Docker (same commands as the CI):

```sh
docker compose build
docker compose up dev                      # migrate + server
docker compose run --rm test               # migrate + suite
docker compose run --rm lint               # ESLint
docker compose run --rm audit              # npm audit (production deps)
```

`db:setup` runs `prisma migrate dev` (creates `storage/development.sqlite3`
and applies migrations) and then the seed.

## Database commands

Prisma reads `DATABASE_URL` from `.env`; the scripts below follow the same
conventions on Windows, macOS and Linux.

| Command | What it does |
| --- | --- |
| `npm run db:setup` | `migrate dev` + `seed` (first run) |
| `npm run db:migrate` | Create/apply a dev migration from schema changes |
| `npm run db:deploy` | Apply existing migrations (CI / test / production) |
| `npm run db:reset` | Drop, re-migrate and re-seed the current database |
| `npm run db:seed` | Load fixtures (idempotent) |
| `npm run db:generate` | Regenerate the Prisma Client |
| `npm run db:studio` | Open Prisma Studio to browse the data |

### Test database

The test suite uses its own SQLite file, `storage/test.sqlite3`, selected
with `DATABASE_URL` (via `cross-env`, so the command works on every OS).
`npm test` migrates it first (`pretest`), so a plain `npm test` just works:

```sh
npm test                # migrate test db + run the suite (serial, --runInBand)
npm run test:watch      # re-run on file changes
npm run test:coverage   # same suite with a coverage report in coverage/
```

The specs share one SQLite file and clean its tables between examples, so
they run serially (`--runInBand`); bare `npx jest` in parallel makes them
fight over the same rows.

## Logger

`config/initializers/logger.js` builds one shared Pino logger from
`config/environments/<APP_ENV>.js`: `debug` in development (every event is
recorded), silent when `APP_ENV=test` (mirroring `App.set :logging, false`, so
the suite output stays readable) and `info` in production, one JSON line per
event. `LOG_LEVEL` overrides the level when it is set.
`src/middleware/request-logger.js` is only installed in the environments whose
settings enable it (`requestLogging`) and then logs one line per request once
the response finishes (`method`, `path`, `status`, `duration_ms`); the error
handler in `lib/errors/errors.js` logs unexpected (500) failures.

## Environments

`APP_ENV` selects the environment (`development`, `test`, `production`), each
with its own settings in `config/environments/*.js` (log level and request
logging) and its own database file, chosen with `DATABASE_URL`, following the
same layout as `ruby-sinatra`'s `data/database.yml`:

| Environment | `DATABASE_URL` |
| --- | --- |
| development | `file:../storage/development.sqlite3` |
| test | `file:../storage/test.sqlite3` |
| production | `file:../storage/production.sqlite3` |

## Seeds

`node db/seeds` (or `npm run db:seed`) loads the same fixtures as the original
and is idempotent. `db/seeds/index.js` only orchestrates the per-resource
loaders under `db/seeds/loaders/`, the way `ruby-sinatra/db/seeds.rb` does; the
data itself lives in YAML files under `db/seeds/data/`, one per resource,
mirroring `ruby-sinatra/db/seeds/*.yml`:

| File | Loader | Identity |
| --- | --- | --- |
| `db/seeds/data/users.yml` | `db/seeds/loaders/users.js` | `email` |
| `db/seeds/data/products.yml` | `db/seeds/loaders/products.js` | `name` |
| `db/seeds/data/payments.yml` | `db/seeds/loaders/payments.js` | `amount` |

- **users** — matched by `email` (stored stripped and lowercased); each
  `password` from the YAML is hashed with bcrypt.
- **products** — matched by `name`.
- **payments** — matched by `amount`; `status` is applied on creation only, so
  a payment confirmed or cancelled through the API is never moved back.

`db/seeds/load-list.js` reads a `data/*.yml` file into a list of records
(the port of Ruby's `load_list`).

Re-running `npm run db:seed` keeps the existing records instead of duplicating
them.

## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request to
`main`/`master` (and on demand via `workflow_dispatch`), with `APP_ENV=test`:

| Job | Runner | What it does |
| --- | --- | --- |
| `test` | matrix 20/22/24 × ubuntu/macOS/windows | `npm ci`, migrate the test database (`npm run test:db:migrate`), `npm test` |
| `lint` | ubuntu-latest | `npm ci` + `npm run lint` (Node from `.node-version`) |
| `audit` | ubuntu-latest | `npm audit --omit=dev` — informative only, does not fail the job |

Two more workflows live under `.github/`:

- `workflows/codeql.yml` — CodeQL analysis of the JavaScript code, on pushes
  and pull requests to `main`, weekly (Sundays, midnight UTC) and on demand.
- `dependabot.yml` — weekly PRs for npm dependencies (Mondays 09:00) and for
  GitHub Actions (Mondays 09:30).

### Running CI locally with act

[act](https://github.com/nektos/act) executes the same workflow in Docker.
The defaults live in [`.actrc`](.actrc) (`-W .github/workflows/ci.yml`, the
container image for every matrix label, `--concurrent-jobs 3`, `--rm`):

```sh
act -l                                              # list the jobs
act                                                 # whole CI workflow
act -j lint                                         # only the lint job
act -j audit                                        # only the audit job
act -j test --matrix node-version:22 --matrix os:ubuntu-latest   # one matrix cell
```

Notes:

- act runs everything in Linux containers, so the macOS and Windows runners
  of the matrix cannot be reproduced; `.actrc` maps their labels to the same
  Linux image used for `ubuntu-latest`.
- The `setup-node` cache-save step may print a `::warning::` when the checkout
  path contains a space (e.g. `HTTP Pardal` on Windows); it does not fail the
  job.
- The CodeQL workflow needs the runner tooling of GitHub-hosted runners and is
  not meant to be run with act.
